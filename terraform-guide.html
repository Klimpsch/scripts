00

Why Terraform exists, and the problem it solves

Before the syntax, the motivation. Terraform is answer to a question every growing network eventually asks: how do I know my devices are configured the way I think they are — and how do I change hundreds of them without it becoming a full-time job of typing?

The problem: configuration drift and the tyranny of "how"

Picture the estate you actually run. Config lives in the running-config of each box, in a pile of change tickets, in a few engineers' heads, and maybe in a backup someone remembers to pull. Over months, reality and documentation quietly diverge. A midnight fix on one switch never makes it back to the "golden" template. A device gets replaced and the replacement is almost the same. This gap between intended and actual state is configuration drift, and it's where outages and audit failures come from.

The traditional tools all describe how to get there — an ordered list of commands to type or a script to run. That works until it doesn't: the same script run twice may double-apply or error; nobody can tell you the current state without logging in and looking; and "make these 200 switches match" becomes 200 careful, fallible repetitions.

The core idea

Terraform flips the model. You write down the desired end state as code, once. Terraform reads the actual state of your devices, computes the difference, and makes only the changes needed to close the gap. Documentation and reality can no longer drift, because the code is the configuration — and it's the thing that gets applied.

What that buys you

Four properties fall out of the declarative-as-code model, and together they're the reason Terraform exists:

Idempotent
Apply once or a hundred times — the result converges to the same state. No double-config, no accumulation.
Visible
A dry-run shows the exact diff before anything changes. State is the always-current record of what's out there.
Versioned
Config lives in Git — peer-reviewed, diffable, revertable. Every change has an author and a reason.
Repeatable
The same module builds device #1 and device #500 identically. Standardization stops being aspirational.

When to reach for Terraform — and when not to

Terraform isn't the only tool in the automation drawer, and it isn't always the right one. It's built to provision and manage the desired state of infrastructure. Other tools are built for other jobs, and reaching for the wrong one is where teams get frustrated.

ToolBuilt forReach for it when…
Terraform Declaring & enforcing the desired state of infrastructure across many devices. You want config as code, drift detection, dry-runs, and repeatable builds at scale — VLANs, OSPF, ACLs, tenants, whole fabrics.
Ansible Procedural task orchestration and one-shot config pushes; strong for OS/app config. You need ordered, step-by-step actions or ad-hoc pushes, and don't need a persistent record of desired state.
Python + Netmiko Bespoke logic, data gathering, and gluing systems together. The task is custom scripting — parsing output, complex conditional logic, integrations no tool models yet.
The CLI / SSH Interactive, immediate control of one device. Troubleshooting, show commands, or a single urgent fix on a single box.
A useful rule of thumb

Ask: "Do I need this to be the same, every time, across many things — and do I need to prove what it looks like?" If yes, that's Terraform's home turf. If you're doing something once, interactively, or writing genuinely custom logic, another tool will serve you better. They're complementary — plenty of shops let Terraform own desired state and call Ansible or scripts for the imperative glue around it.

01

The lifecycle: init, plan, apply, destroy

Four commands run the whole show. Think of them as the config-mode workflow for an entire fabric: connect, dry-run the diff, commit, and — when a lab is done — tear it all back down cleanly.

init
Downloads the provider plugin and prepares the backend. Run once per project.
plan
Dry run. Diffs desired state against reality and prints exactly what will change.
apply
Executes the plan. Pushes config to the devices and records the result in state.
destroy
Removes everything Terraform created — in reverse dependency order.

Point Terraform at a real device

Every project starts with a provider block. This is your authentication and transport — the equivalent of an SSH session with credentials and a target IP. Below, IOS XE talks to a device over RESTCONF.

providers.tfHCL 
terraform {
  required_providers {
    iosxe = {
      source  = "CiscoDevNet/iosxe"
      version = "~> 0.5"
    }
  }
}

# Transport + credentials — one block per managed device
provider "iosxe" {
  username = "admin"
  password = var.device_password   # never hard-code secrets
  url      = "https://192.0.2.10"     # RESTCONF endpoint
  insecure = true                     # lab only; use real certs in prod
}
Provider = feature set

Swap the provider, keep the workflow. cisco/meraki talks to the Dashboard API for cloud-managed switching and wireless; cisco/aci models tenants, bridge domains, and EPGs against the APIC. The four lifecycle commands never change — only the resources you declare do.

init — prepare the working directory

terminalCLI + output
$ terraform init

Initializing provider plugins...
- Finding ciscodevnet/iosxe versions matching "~> 0.5"...
- Installing ciscodevnet/iosxe v0.5.7...
- Installed ciscodevnet/iosxe v0.5.7 (signed by a HashiCorp partner)

Terraform has been successfully initialized!

Behind the scenes: Terraform reads required_providers, pulls the plugin binary into .terraform/, and writes a .terraform.lock.hcl so every teammate gets the identical provider version. Analogous to standardizing an IOS image across a stack before you push config.

plan — the dry run you always wanted

This is the safety net a network engineer will love most. Nothing touches the device. Terraform builds a dependency graph, compares your files to recorded state, and prints a show run-style diff of intended changes.

terminalCLI + output
$ terraform plan

Terraform will perform the following actions:

  # iosxe_vlan.data will be created
  + resource "iosxe_vlan" "data" {
      + vlan_id = 120
      + name    = "USERS_DATA"
    }

Plan: 1 to add, 0 to change, 0 to destroy.

Note: You didn't use the -out option to save this plan.
Read the symbols like a diff

+ create · - destroy · ~ update in place · -/+ replace (destroy then recreate). A plan full of unexpected -/+ replacements is your cue to stop and investigate before applying.

apply — commit to the fabric

terminalCLI + output
$ terraform apply

# ...same plan is reprinted...
Do you want to perform these actions?
  Terraform will perform the actions described above.
  Only 'yes' will be accepted to approve.

  Enter a value: yes

iosxe_vlan.data: Creating...
iosxe_vlan.data: Creation complete after 2s [id=Cisco-IOS-XE-native:vlan/120]

Apply complete! Resources: 1 added, 0 changed, 0 destroyed.

Terraform now pushes config over RESTCONF, waits for each device to confirm, and records the real-world object in state. Add -auto-approve in CI pipelines; keep the interactive prompt for anything touching production.

destroy — reverse-order teardown

Perfect for lab pods and ephemeral environments. Terraform walks the dependency graph backwards so it removes an SVI before the VLAN it depends on, never orphaning config.

terminalCLI + output
$ terraform destroy

iosxe_vlan.data: Destroying... [id=Cisco-IOS-XE-native:vlan/120]
iosxe_vlan.data: Destruction complete after 1s

Destroy complete! Resources: 0 added, 0 changed, 1 destroyed.
02

The same VLAN, OSPF, and ACL — declared once

Here's the mental shift. On the CLI you type a sequence of commands and the box appends them. In Terraform you write the end state and Terraform figures out the commands. Re-run it ten times: the result is identical. That's convergence, and it's the whole point.

VLAN + access port

Left is what you'd type today. Right is the desired state. Both create VLAN 120 and drop Gi1/0/5 into it.

IOS CLI — procedural
config terminalIOS
vlan 120
 name USERS_DATA
!
interface Gi1/0/5
 switchport mode access
 switchport access vlan 120
!
end
write memory
Terraform — declarative
vlans.tfHCL
resource "iosxe_vlan" "data" {
  vlan_id = 120
  name    = "USERS_DATA"
}

resource "iosxe_interface_ethernet" "gi5" {
  name             = "1/0/5"
  switchport_access_vlan = 120
  switchport_mode_access = true
}
Convergence, not accumulation

Change 120 to 130 and re-apply. The CLI would leave VLAN 120 behind and add 130. Terraform sees state drift and issues the exact reconfigure to match the file — the old VLAN is removed. Your files are always the source of truth.

OSPF process, area, and networks

IOS CLI — procedural
config terminalIOS
router ospf 10
 router-id 10.0.0.1
 network 10.10.0.0 0.0.255.255 area 0
 network 10.20.0.0 0.0.255.255 area 0
 passive-interface default
 no passive-interface Gi1/0/1
!
end
Terraform — declarative
ospf.tfHCL
resource "iosxe_router_ospf" "core" {
  process_id = 10
  router_id  = "10.0.0.1"

  networks {
    ip           = "10.10.0.0"
    wildcard     = "0.0.255.255"
    area         = "0"
  }
  networks {
    ip           = "10.20.0.0"
    wildcard     = "0.0.255.255"
    area         = "0"
  }
  passive_interface_default = true
}

Named ACL with multiple ACEs

An ordered list of ACEs maps cleanly to an ordered list of nested blocks. Sequence numbers keep ACE order deterministic across applies.

IOS CLI — procedural
config terminalIOS
ip access-list extended GUEST_IN
 10 permit tcp 10.30.0.0 0.0.255.255
    any eq 443
 20 permit udp 10.30.0.0 0.0.255.255
    any eq 53
 30 deny   ip  10.30.0.0 0.0.255.255
    10.0.0.0 0.255.255.255
 40 permit ip  any any
!
end
Terraform — declarative
acl.tfHCL
resource "iosxe_extended_acl" "guest" {
  name = "GUEST_IN"

  rules {
    sequence = 10
    action   = "permit"
    protocol = "tcp"
    source          = "10.30.0.0"
    source_wildcard = "0.0.255.255"
    destination_any = true
    destination_port_equal = 443
  }
  rules {
    sequence = 40
    action   = "permit"
    protocol = "ip"
    source_any      = true
    destination_any = true
  }
  # ...ACEs 20 and 30 follow the same shape
}
Order still matters

An ACL is one of the few network constructs where sequence is semantic — first match wins. Terraform preserves your sequence numbers exactly, so the declarative model doesn't lose the ordering guarantee you rely on. Leave gaps (10, 20, 30) so you can insert later.

03

State: how Terraform remembers the network

Terraform's superpower — knowing the difference between what you want and what's out there — depends entirely on a JSON file called state. Understand this file and everything else clicks.

What terraform.tfstate actually holds

State is the map between your resource names and the real objects on the devices. When you write iosxe_vlan.data, state records that this corresponds to VLAN 120 on 192.0.2.10, plus every attribute Terraform last saw. On the next plan, Terraform reads state, reads your files, and diffs the two.

terraform.tfstateJSON — generated
{
  "resources": [{
    "type": "iosxe_vlan",
    "name": "data",
    "instances": [{
      "attributes": {
        "id":      "Cisco-IOS-XE-native:vlan/120",
        "vlan_id": 120,
        "name":    "USERS_DATA"
      }
    }]
  }]
}
Why local state bites teams

A terraform.tfstate sitting on your laptop causes three real problems: no locking — two engineers apply at once and corrupt it; drift & divergence — your teammate's copy doesn't know about your changes; and secrets in plaintext — any sensitive attribute a provider returns lands in this file unencrypted. Never commit it to Git.

Remote state: the shared source of truth

Move state off the laptop into a shared backend. Now the file lives once, centrally; Terraform locks it during any operation so concurrent applies are impossible; and it's encrypted at rest. This is the single most important step before more than one person touches a project.

Option A — S3 with DynamoDB locking

backend.tfHCL
terraform {
  backend "s3" {
    bucket         = "netops-tfstate"
    key            = "campus/core-switches.tfstate"
    region         = "us-east-1"
    dynamodb_table = "tf-locks"   # state locking
    encrypt        = true          # encrypt at rest
  }
}

Option B — Terraform Cloud / HCP

backend.tfHCL
terraform {
  cloud {
    organization = "acme-netops"
    workspaces { name = "campus-core" }
  }
}

Locking is automatic here, state is encrypted and versioned, and every apply is logged with who ran it and what changed — an audit trail your change-management process will thank you for. Run terraform init after adding a backend to migrate existing state into it.

The locking analogy

A state lock is the config-lock exclusive semaphore you already know from configure exclusive — it stops a second session from making concurrent changes to the same device. Remote state gives that same guarantee across a whole team, automatically.

04

Declarative vs procedural

You've now seen both models in the same room. The question isn't which is "better" — it's which fits the job. Here's how they compare on the four axes that decide it: scale, skills, reusability, and speed.

Procedural (the IOS CLI, a Netmiko/Python script, an Ansible playbook run imperatively) describes how — an ordered sequence of steps. Declarative (Terraform) describes what — the end state — and lets the engine compute the steps. Terraform 1.5 sharpens the declarative edge with import blocks (bring existing devices under management from a file, no manual CLI import) and check blocks (assert post-apply conditions like "the OSPF neighbor is up").

AxisProcedural — CLI / scriptsDeclarative — Terraform
Scale Linear effort — 200 switches means running the sequence 200 times and tracking which succeeded. One config, for_each over an inventory. The graph fans out to 200 devices in parallel from a single apply.
Skills Leans on deep per-platform CLI fluency and scripting to handle idempotency and error paths yourself. Leans on modeling intent in HCL. The provider handles idempotency, ordering, and retries — less code to babysit.
Reusability Scripts get copy-pasted and forked; drift creeps in between copies over time. Modules are versioned and parameterized. Define an "access-switch" once, instantiate it everywhere with variables.
Speed Fast to write for a one-off change; slow and risky to safely repeat, review, or roll back at scale. Upfront modeling cost, then near-instant repeatable changes with a built-in dry-run and clean teardown.
The honest verdict

For a single urgent change on one box at 2 a.m., the CLI still wins — reach for it. Declarative pays off when a change must be repeatable, reviewable, and applied across many devices the same way every time. Most production network estates eventually cross that line, which is why IaC has moved from the server world into the network.

Where each one shines

Reach for procedural when…
• A one-off fix on a single device
• Interactive troubleshooting & show cmds
• Steps genuinely must run in a fixed
  order with side effects
• No shared team ownership of the config
Reach for declarative when…
• The same change hits many devices
• You want a dry-run before every commit
• Config should live in Git, peer-reviewed
• You need clean, ordered teardown
• Drift detection matters to compliance
