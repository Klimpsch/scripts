01

REST API fundamentals

A REST API (Representational State Transfer) is a way for programs to talk to a service over ordinary HTTP. Instead of clicking through a web console, you send an HTTP request to a URL and get back structured data — almost always JSON. For an administrator this is the difference between manually toggling a server's power in a browser and having a script do it for a hundred servers at 2 a.m.

Resources and endpoints

REST models everything as a resource — a server, a virtual machine, a user, a power state. Each resource lives at an endpoint, which is just a URL. The pattern is a base URL plus a path that reads like a folder tree:

endpoint anatomyhttp
# base URL          resource path             query string
https://idrac.lab.local /redfish/v1/Systems/System.Embedded.1 ?param=value
└──── scheme + host ───┘└──────── path (the resource) ───────┘└─ filters ─┘

HTTP methods (verbs)

The method tells the server what you want to do to the resource. The same URL behaves differently depending on the verb.

MethodIntentTypical useSafe / Idempotent
GETRead a resourceFetch VM list, read power stateYes / Yes
POSTCreate or trigger an actionCreate a session, issue a rebootNo / No
PUTReplace a resource wholesaleOverwrite a full config objectNo / Yes
PATCHModify part of a resourceChange one BIOS attributeNo / No*
DELETERemove a resourceLog out (delete a session)No / Yes

*PATCH idempotency depends on the payload; a PATCH that sets an absolute value is idempotent, one that increments is not.

Status codes

Every response carries a numeric status code. Learn the families and you can debug most failures at a glance.

RangeMeaningCommon ones you'll see
2xxSuccess200 OK, 201 Created, 202 Accepted, 204 No Content
3xxRedirection301 Moved, 304 Not Modified
4xxYou made a mistake400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 429 Too Many Requests
5xxThe server broke500 Internal Error, 503 Service Unavailable
5.1
In PowerShell 5.1, any non-2xx status makes Invoke-RestMethod throw a terminating error. You do not get the response object back through the normal return value — you have to dig it out of the exception (covered in §3). This is different from PowerShell 7's -SkipHttpErrorCheck.

Headers

Headers are metadata sent alongside the request and response. The ones you'll touch most:

  • Content-Type: application/json — tells the server your body is JSON.
  • Accept: application/json — tells the server what you want back.
  • Authorization: Bearer <token> — proves who you are.
  • Vendor-specific session headers, e.g. iDRAC returns an X-Auth-Token you reuse on later calls.

Request and response bodies

The body carries the actual data. On a POST or PATCH you send JSON in; on a GET you get JSON back. A power-off action to a Redfish endpoint has a tiny body like this:

request bodyjson
{ "ResetType": "GracefulShutdown" }

Authentication — the four you'll meet

TypeHow it worksWhere you'll see it
BasicBase64 of user:pass in an Authorization header, sent every requestiDRAC Redfish (simplest mode), many appliances
Bearer / tokenYou log in once, get a token, send Authorization: Bearer <token> afterCloud APIs, modern REST services
API keyA long static secret in a header or query stringSaaS & monitoring platforms
Session tokenPOST credentials → server returns a session ID/cookie you reuse, then delete on logoutvSphere REST, iDRAC session mode
→
Session tokens are the polite choice for hardware like iDRAC and ESXi: authenticate once, reuse the token, and log out. Sending Basic auth on every call re-hits the login subsystem and, on some BMCs, contributes to lockouts.
02

Calling APIs in PowerShell 5.1

PowerShell gives you two cmdlets. Pick by what you want back:

  • Invoke-RestMethod (IRM) — automatically parses JSON into PowerShell objects. This is your default for REST work.
  • Invoke-WebRequest (IWR) — returns the full HTTP response: status code, headers, and raw content. Use it when you need the status code or response headers (e.g. to grab a session token).

A minimal GET

simple-get.ps1powershell
# IRM returns parsed objects — no ConvertFrom-Json needed
$data = Invoke-RestMethod -Uri "https://api.example.com/v1/servers" -Method Get

# Now $data is a real object you can pipe and filter
$data.value | Where-Object { $_.status -eq "on" } | Select-Object name, id

Headers, JSON body, and query parameters

Build a hashtable of headers, convert a hashtable to a JSON body with ConvertTo-Json, and either append query params to the URI or splat the whole call for readability.

post-with-body.ps1powershell
# 1) Headers as a hashtable
$headers = @{
    "Content-Type"  = "application/json"
    "Accept"        = "application/json"
    "Authorization" = "Bearer $token"
}

# 2) Build the body as an object, then serialize.
#    -Depth matters: 5.1 defaults to Depth 2 and SILENTLY truncates nested data.
$bodyObj = @{
    name     = "web-01"
    tags     = @("prod", "linux")
    settings = @{ cpu = 4; ram = 16 }
}
$body = $bodyObj | ConvertTo-Json -Depth 10

# 3) Query parameters — either inline or via a hashtable you join
$query  = @{ limit = 50; offset = 0 }
$qs     = ($query.GetEnumerator() | ForEach-Object { "$($_.Key)=$($_.Value)" }) -join "&"
$uri    = "https://api.example.com/v1/servers?$qs"

# 4) Splat the call — cleaner than a 5-line one-liner
$params = @{
    Uri     = $uri
    Method  = "Post"
    Headers = $headers
    Body    = $body
}
$result = Invoke-RestMethod @params
5.1
Always pass -Depth to ConvertTo-Json. Windows PowerShell 5.1 defaults to a depth of only 2 and truncates deeper structures without warning — a classic cause of "the API rejected my body and I can't see why." PowerShell 7 raised the effective default and warns on truncation; 5.1 does neither.

Authentication in practice

Using -Credential (Basic auth)

cred-basic.ps1powershell
# Prompt securely — password never appears in the script or history
$cred = Get-Credential

# PS 5.1 quirk: for many appliances you must also pass -Authentication Basic
# is NOT available in 5.1. Instead PS 5.1 only sends Basic auth AFTER a 401
# challenge. Some devices don't challenge — so build the header manually (below).
$resp = Invoke-RestMethod -Uri "https://device/api" -Credential $cred

Building the Basic auth header by hand (the reliable way)

Because 5.1's -Credential only sends Basic auth after a 401 challenge — and many BMCs don't challenge — the robust pattern is to construct the header yourself so it's sent on the first request.

manual-basic-header.ps1powershell
$user = "admin"
$pass = "P@ssw0rd!"

# Encode "user:pass" as Base64 for the Authorization header
$pair   = "$($user):$($pass)"
$bytes  = [System.Text.Encoding]::ASCII.GetBytes($pair)
$b64    = [System.Convert]::ToBase64String($bytes)

$headers = @{ Authorization = "Basic $b64" }
$resp    = Invoke-RestMethod -Uri "https://device/api" -Headers $headers

Bearer token after a login call

bearer-flow.ps1powershell
# Step 1: log in, receive a token
$login = Invoke-RestMethod -Uri "https://api.example.com/auth" -Method Post -Body (
    @{ username = "admin"; password = "secret" } | ConvertTo-Json
) -ContentType "application/json"

$token = $login.access_token

# Step 2: reuse the token on every subsequent call
$auth  = @{ Authorization = "Bearer $token" }
$me    = Invoke-RestMethod -Uri "https://api.example.com/me" -Headers $auth

Parsing responses

With IRM the response is already an object. With IWR you get the envelope and parse the content yourself:

parse-iwr.ps1powershell
$r = Invoke-WebRequest -Uri "https://api.example.com/v1/vms" -Headers $auth

$r.StatusCode                 # 200
$r.Headers["X-Auth-Token"]     # read a specific response header
$obj = $r.Content | ConvertFrom-Json   # turn raw text into objects
$obj.value | Format-Table name, power_state

The self-signed certificate problem

iDRAC, ESXi, and most lab appliances ship with self-signed TLS certificates. PowerShell 5.1 will refuse to connect and throw "The underlying connection was closed: Could not establish trust relationship...". Version 7 solved this cleanly with -SkipCertificateCheck — that parameter does not exist in 5.1. You must override the .NET certificate validation callback and force TLS 1.2.

5.1
Windows PowerShell 5.1 often negotiates TLS 1.0/1.1 by default. Modern appliances reject those, giving the same "connection closed" error even when the cert is valid. Fix both problems together — trust callback and TLS 1.2.
tls-and-cert-bypass.ps1powershell
# === Run once per session, BEFORE any Invoke-* call ===

# 1) Force TLS 1.2 (5.1 may default to 1.0/1.1)
[System.Net.ServicePointManager]::SecurityProtocol = `
    [System.Net.SecurityProtocolType]::Tls12

# 2) Trust ALL certificates (lab/self-signed only — see warning)
[System.Net.ServicePointManager]::ServerCertificateValidationCallback = `
    { $true }
!
Security warning. The callback above trusts every certificate for the whole process, disabling MITM protection. Acceptable on an isolated management network to a known iDRAC/ESXi host; never do this against internet endpoints or in shared automation. The cleaner long-term fix is to import the device's certificate into the trusted store, or replace the appliance cert with one from your CA.

A more surgical alternative validates the specific thumbprint instead of blindly returning $true:

pin-thumbprint.ps1powershell
$expected = "A1B2C3D4E5F6..."   # the device's known cert thumbprint

[System.Net.ServicePointManager]::ServerCertificateValidationCallback = {
    param($sender, $cert, $chain, $errors)
    return ($cert.GetCertHashString() -eq $expected)
}
03

Testing & troubleshooting

Explore before you script

Don't write 40 lines against an endpoint you've never hit. Probe it first with a GUI or one-liner, learn the response shape, then codify it.

  • Postman / Insomnia — click-driven; great for discovering the auth flow, headers, and JSON shape. Postman can even export a working request as PowerShell.
  • curl — ships with Windows 10/11 as curl.exe. Note that in PowerShell curl is an alias for Invoke-WebRequest, so call curl.exe explicitly to get real curl.
quick-probebash
# Real curl (note .exe), -k skips cert check, -i shows response headers
curl.exe -k -i -u admin:calvin `
  https://idrac.lab.local/redfish/v1/Systems/System.Embedded.1

Use -Verbose to see the wire

Adding -Verbose to any Invoke-* call prints the request URI, method, and content type — invaluable when a call silently does the wrong thing.

verbose.ps1powershell
Invoke-RestMethod -Uri $uri -Headers $headers -Verbose

Error handling: try / catch and reading the response

Because 5.1 throws on any 4xx/5xx, wrap real calls in try/catch. The trick is that the useful information — the status code and the server's error body — lives on $_.Exception.Response, not in the thrown message.

robust-call.ps1powershell
try {
    $resp = Invoke-RestMethod -Uri $uri -Headers $headers -Method Post -Body $body
}
catch {
    # 1) The HTTP status code
    $status = $_.Exception.Response.StatusCode.value__
    Write-Warning "HTTP $status calling $uri"

    # 2) The server's error BODY — often the real explanation.
    #    In 5.1 you read it off the underlying response stream.
    if ($_.Exception.Response) {
        $stream = $_.Exception.Response.GetResponseStream()
        $reader = New-Object System.IO.StreamReader($stream)
        $reader.BaseStream.Position = 0
        $errorBody = $reader.ReadToEnd()
        Write-Host "Server said: $errorBody" -ForegroundColor Red
    }
    throw   # re-throw if the caller should still fail
}
5.1
In PowerShell 7 the error body is handed to you as $_.ErrorDetails.Message — no stream reading required. The GetResponseStream() dance above is a 5.1-specific necessity. Note also that $_.ErrorDetails.Message sometimes populates in 5.1 too; check it first and fall back to the stream.

Common 5.1 pitfalls

SymptomCauseFix
"Could not establish trust relationship"Self-signed cert and/or TLS 1.0 defaultSet TLS 1.2 + cert callback (§2)
Body silently missing nested fieldsConvertTo-Json default depth of 2Add -Depth 10
401 despite correct password with -CredentialDevice doesn't send a 401 challenge, so 5.1 never sends Basic authBuild the header manually

Non-ASCII characters mangledEncoding of bodySerialize/encode as UTF-8 explicitly

→
Add -UseBasicParsing to every Invoke-WebRequest in 5.1. Without it, IWR tries to use the Internet Explorer DOM engine, which is slow, can hang on servers without IE configured, and is removed in PowerShell 7 anyway (where it's the default behavior).
04

Best practices

Never hard-code credentials

Plaintext passwords in a .ps1 end up in source control, screen shares, and shoulder-surfs. Prefer, in order:

  1. Get-Credential for interactive runs — the password lives only in memory as a SecureString.
  2. An encrypted credential file scoped to the user + machine for unattended runs.
  3. A real secret store (Windows Credential Manager via the CredentialManager module, or Microsoft.PowerShell.SecretManagement).
encrypted-cred-file.ps1powershell
# --- One-time: save an encrypted credential (DPAPI, per user + machine) ---
Get-Credential | Export-Clixml "C:\secure\idrac.cred.xml"

# --- In the script: load it back, no prompt, no plaintext ---
$cred = Import-Clixml "C:\secure\idrac.cred.xml"

# Pull the plaintext ONLY at the moment you build the auth header
$user = $cred.UserName
$pass = $cred.GetNetworkCredential().Password
!
Export-Clixml encryption is tied to the user account and machine that created it (Windows DPAPI). The file can only be decrypted by that same user on that same box — which is exactly what you want for scheduled tasks, but means you can't just copy the file to another server.

Pagination

APIs cap how many items they return per call. Loop until there's no "next" link or you've collected everything.

paginate.ps1powershell
$all  = @()
$uri  = "https://api.example.com/v1/items?limit=100"

do {
    $page = Invoke-RestMethod -Uri $uri -Headers $auth
    $all += $page.value
    $uri  = $page.'@odata.nextLink'   # null when no more pages
} while ($uri)

Write-Host "Collected $($all.Count) items"

Rate limiting & retry with backoff

Respect 429 Too Many Requests and transient 5xx errors with exponential backoff. A reusable wrapper keeps every call resilient.

invoke-with-retry.ps1powershell
function Invoke-ApiWithRetry {
    param(
        [hashtable]$Params,
        [int]$MaxAttempts = 5
    )
    for ($i = 1; $i -le $MaxAttempts; $i++) {
        try {
            return Invoke-RestMethod @Params
        }
        catch {
            $code = $_.Exception.Response.StatusCode.value__
            # Retry only on rate limit or server errors
            if ($code -eq 429 -or $code -ge 500) {
                $wait = [math]::Pow(2, $i)   # 2,4,8,16,32 s
                Write-Warning "HTTP $code — retry $i in $wait s"
                Start-Sleep -Seconds $wait
            }
            else { throw }   # 4xx (except 429) won't fix itself
        }
    }
    throw "Failed after $MaxAttempts attempts"
}
→
If the response includes a Retry-After header, honor that value instead of your own backoff — it's the server telling you exactly how long to wait.

Idempotency

Design retries around whether the operation is safe to repeat. GET, PUT, and DELETE are idempotent — running them twice leaves the same end state. POST generally is not (retrying "create VM" can make two VMs). Only auto-retry non-idempotent calls when the API offers an idempotency key or you can first check whether the action already succeeded.

Timeouts

A hung BMC shouldn't hang your whole run. Always bound requests.

timeout.ps1powershell
Invoke-RestMethod -Uri $uri -Headers $auth -TimeoutSec 30

Logging

Log what you called, when, the status, and the outcome — not the secrets. A transcript plus structured lines makes 2 a.m. debugging bearable.

logging.ps1powershell
Start-Transcript -Path "C:\logs\idrac-run-$(Get-Date -f yyyyMMdd-HHmmss).log"

Write-Host "[$(Get-Date -f o)] POST $uri -> $($resp.StatusCode)"

Stop-Transcript
!
Scrub tokens and passwords before logging. A Bearer token in a log file is a live credential. Mask everything after the first few characters, or don't log the header at all.
05

Advanced patterns

The basics get you a working call. These patterns get you a client that survives real APIs — ones that expire tokens, throttle you, paginate everything, and answer with a status code you have to interpret rather than just succeed or fail on.

OAuth2 with token refresh

Many modern APIs issue a short-lived access token (often 5–60 minutes) plus a long-lived refresh token. Rather than re-sending your password, you exchange the refresh token for a new access token when the old one expires. The robust approach: store the expiry, and refresh before a call if the token is stale or about to be.

oauth2-refresh.ps1powershell
# ---- Initial token grant (client credentials or password grant) ----
$tokenUri = "https://auth.example.com/oauth2/token"

$grant = Invoke-RestMethod -Uri $tokenUri -Method Post -Body @{
    grant_type    = "client_credentials"
    client_id     = $clientId
    client_secret = $clientSecret
    scope         = "api.read api.write"
}   # form-encoded body — pass a hashtable, NOT ConvertTo-Json, for OAuth token calls

# Track the token AND when it dies. expires_in is seconds from now.
$script:token       = $grant.access_token
$script:refresh     = $grant.refresh_token
$script:tokenExpiry = (Get-Date).AddSeconds($grant.expires_in)

function Get-ValidToken {
    # Refresh 60 s early to avoid a race where the token dies mid-call
    if ((Get-Date) -ge $script:tokenExpiry.AddSeconds(-60)) {
        Write-Verbose "Access token stale — refreshing"
        $new = Invoke-RestMethod -Uri $tokenUri -Method Post -Body @{
            grant_type    = "refresh_token"
            refresh_token = $script:refresh
            client_id     = $clientId
            client_secret = $clientSecret
        }
        $script:token       = $new.access_token
        $script:tokenExpiry = (Get-Date).AddSeconds($new.expires_in)
        # Some providers rotate the refresh token too — capture it if present
        if ($new.refresh_token) { $script:refresh = $new.refresh_token }
    }
    return $script:token
}

# Every call fetches a guaranteed-valid token first
$auth = @{ Authorization = "Bearer $(Get-ValidToken)" }
$data = Invoke-RestMethod -Uri "https://api.example.com/v1/things" -Headers $auth
5.1
OAuth token endpoints expect a form-encoded body (application/x-www-form-urlencoded), not JSON. In PowerShell 5.1, passing a plain hashtable to -Body form-encodes it automatically — so do not pipe it through ConvertTo-Json for the token grant. JSON is only for the API calls that follow.

Session reuse

Refreshing a token or re-authenticating on every call is wasteful and, on hardware like iDRAC, can exhaust the session pool. Authenticate once, cache the token/session in a variable, and reuse it for the life of the run. Two reuse styles:

StyleHowBest for
Header reuseStore the token/session-id and pass the same -Headers hashtable to every callToken & session APIs (iDRAC, vSphere, OAuth)
WebSession objectCapture cookies with -SessionVariable, then pass -WebSession so auth cookies + connection settings persistCookie-based auth, keeping TCP connections warm
websession-reuse.ps1powershell
# First call creates a session object bound to $sv (note: no $ in -SessionVariable)
Invoke-RestMethod -Uri "https://api.example.com/login" -Method Post `
    -Body $loginBody -ContentType "application/json" -SessionVariable sv | Out-Null

# Every later call reuses cookies, headers, and the warm connection via $sv
$profile = Invoke-RestMethod -Uri "https://api.example.com/me"    -WebSession $sv
$orders  = Invoke-RestMethod -Uri "https://api.example.com/orders" -WebSession $sv
→
Reusing a WebSession also reuses the underlying TCP/TLS connection, which noticeably speeds up loops of many calls to the same host — you pay the TLS handshake once instead of per request.

Retry-After & exponential backoff

The retry wrapper in §4 backs off on its own schedule. A well-behaved client should first honor the server's Retry-After header when present (seconds, or an HTTP date), and only fall back to exponential backoff otherwise.

retry-after-aware.ps1powershell
function Get-RetryDelay {
    param($Exception, [int]$Attempt)

    # 1) Prefer the server's Retry-After header if it sent one
    $retryAfter = $Exception.Response.Headers["Retry-After"]
    if ($retryAfter) {
        # Header may be seconds ("30") or an HTTP date
        if ($retryAfter -match '^\d+$') {
            return [int]$retryAfter
        }
        $when = [datetime]$retryAfter
        return [math]::Max(1, ($when - (Get-Date)).TotalSeconds)
    }

    # 2) Otherwise exponential backoff with jitter (avoid thundering herd)
    $base   = [math]::Pow(2, $Attempt)          # 2,4,8,16...
    $jitter = Get-Random -Minimum 0 -Maximum 1000   # ms
    return $base + ($jitter / 1000)
}

Status-code branching

"Did it throw?" is too blunt. A robust client branches on the actual code: some 4xx are permanent (don't retry), 401 means refresh-and-retry-once, 429 and 5xx mean back off and retry, and 404 may be a legitimate "not found" your caller should handle rather than an error.

status-branching.ps1powershell
catch {
    $code = $_.Exception.Response.StatusCode.value__

    switch ($code) {
        401 {
            # Token expired — refresh once and let the caller retry
            Write-Verbose "401 — token expired, refreshing"
            Get-ValidToken | Out-Null
            $shouldRetry = $true
        }
        403 { throw "403 Forbidden — permissions issue, will not retry" }
        404 {
            # Not an error for us — return null so caller decides
            Write-Verbose "404 — resource not found"
            return $null
        }
        429     { $shouldRetry = $true }   # rate limited
        {$_ -ge 500} { $shouldRetry = $true }   # server error
        default { throw }                    # other 4xx: permanent, re-throw
    }
}
06

Build one robust API client

Everything above — TLS setup, token refresh, session reuse, Retry-After, backoff, status branching, pagination, logging — belongs in one reusable function you call everywhere, instead of scattered across every script. This is the payoff: a single Invoke-ApiRequest that every other call goes through. Write it once, and every consumer inherits the resilience.

→
The function below is self-contained and pastes into any 5.1 script. It handles TLS, auth injection, automatic 401 refresh, Retry-After-aware backoff, status branching, and a bounded retry loop. Swap the Get-ValidToken call for your own auth (Basic header, session id, etc.).
Invoke-ApiRequest.ps1 — the one clientpowershell
# ============================================================
#  Invoke-ApiRequest — a resilient REST client for PS 5.1
#  Handles: TLS 1.2, auth, 401-refresh, 429/5xx retry with
#  Retry-After + backoff, status branching, and logging.
# ============================================================

# Run TLS/cert prep ONCE at module load, not per call
[Net.ServicePointManager]::SecurityProtocol = [Net.SecurityProtocolType]::Tls12

function Invoke-ApiRequest {
    [CmdletBinding()]
    param(
        [Parameter(Mandatory)][string]$Uri,
        [ValidateSet("Get","Post","Put","Patch","Delete")]
        [string]$Method      = "Get",
        $Body,                       # hashtable/object; auto-JSON below
        [hashtable]$Headers = @{},
        [int]$TimeoutSec   = 30,
        [int]$MaxAttempts  = 5
    )

    # Inject a fresh bearer token every call (see §5 Get-ValidToken)
    $Headers["Authorization"] = "Bearer $(Get-ValidToken)"

    # Serialize object bodies to JSON with a safe depth (5.1 caveat)
    $jsonBody = $null
    if ($Body) {
        $jsonBody = if ($Body -is [string]) { $Body }
                    else { $Body | ConvertTo-Json -Depth 10 }
    }

    for ($attempt = 1; $attempt -le $MaxAttempts; $attempt++) {
        try {
            $p = @{
                Uri         = $Uri;      Method  = $Method
                Headers     = $Headers;  TimeoutSec = $TimeoutSec
                ErrorAction = "Stop"
            }
            if ($jsonBody) {
                $p.Body        = $jsonBody
                $p.ContentType = "application/json"
            }
            Write-Verbose "[$(Get-Date -f o)] $Method $Uri (attempt $attempt)"
            return Invoke-RestMethod @p        # SUCCESS — exit here
        }
        catch {
            $resp = $_.Exception.Response
            $code = if ($resp) { $resp.StatusCode.value__ } else { 0 }

            switch ($code) {
                401 {
                    Write-Verbose "401 — refreshing token, retrying"
                    $Headers["Authorization"] = "Bearer $(Get-ValidToken)"
                }
                404 { return $null }                # caller handles absence
                403 { throw "403 Forbidden: $Uri" }
                429     { }                          # fall through to backoff
                {$_ -ge 500} { }                     # fall through to backoff
                default {
                    # Permanent 4xx (400/409/422...) — surface the body
                    if ($resp) {
                        $r = New-Object IO.StreamReader($resp.GetResponseStream())
                        $r.BaseStream.Position = 0
                        Write-Warning ($r.ReadToEnd())
                    }
                    throw
                }
            }

            if ($attempt -eq $MaxAttempts) { throw "Gave up after $MaxAttempts attempts: $Uri" }

            $delay = Get-RetryDelay -Exception $_.Exception -Attempt $attempt
            Write-Warning "HTTP $code — waiting $delay s (attempt $attempt/$MaxAttempts)"
            Start-Sleep -Seconds $delay
        }
    }
}

Pagination on top of the client

Because every call now goes through one hardened function, pagination becomes a thin loop that inherits all the resilience for free:

get-all-pages.ps1powershell
function Get-AllPages {
    param([string]$Uri)
    $all = @()
    do {
        $page = Invoke-ApiRequest -Uri $Uri          # retries, refresh, backoff — all free
        $all += $page.value
        $Uri  = $page.'@odata.nextLink'            # or $page.links.next, per API
    } while ($Uri)
    return $all
}

# Usage — one line, fully resilient
$servers = Get-AllPages -Uri "https://api.example.com/v1/servers?limit=100"
Write-Host "Retrieved $($servers.Count) servers across all pages"
→
Why this matters: without a shared client, every script re-implements TLS, retries, and refresh — and each does it slightly differently, so bugs hide in the gaps. One Invoke-ApiRequest means one place to fix, one place to test, and consistent behavior across your whole toolkit. Drop it in a .psm1 module and Import-Module it everywhere.
07

Pros & cons of PowerShell 5.1 for REST

PowerShell 5.1 is Windows PowerShell — the last of the .NET Framework line, frozen in feature terms but installed and enabled on every supported Windows Server and client. That ubiquity is its whole value proposition, and also the source of its friction.

Pros

  • Already there. On every Windows box since Server 2016 / Win 10 — nothing to install, nothing to get approved.
  • Zero dependencies. Invoke-RestMethod is built in; no modules, no runtime.
  • First-class objects. IRM parses JSON into real objects you can pipe, filter, and format natively.
  • Deep Windows integration. Scheduled Tasks, Credential Manager/DPAPI, WinRM, AD — all right there.
  • Stable & predictable. Frozen feature set means scripts written today behave the same in five years.

Cons

  • No -SkipCertificateCheck. Self-signed certs force the global callback hack.
  • TLS 1.2 not default. Must be set manually or modern endpoints refuse the handshake.
  • Shallow JSON depth. ConvertTo-Json truncates at depth 2 silently.
  • Clumsy error bodies. No -SkipHttpErrorCheck; reading a 4xx body means stream-reading the exception.
  • IWR uses the IE engine. Needs -UseBasicParsing; slow and can hang.
  • No parallelism. No ForEach-Object -Parallel; big fleets run serially or need runspaces.
  • End of the line. Bug fixes only — all new investment is in PowerShell 7+.
→
When to reach for PowerShell 7 instead: if you can install it, PS 7 removes nearly every con above — -SkipCertificateCheck, TLS 1.2 by default, sane error bodies via -SkipHttpErrorCheck and $_.ErrorDetails.Message, parallel loops, and better ConvertTo-Json. Use 5.1 when you can't install anything; use 7 when you can.

Example — Dell iDRAC (Redfish API)

◆ Dell iDRAC · Redfish v1

Redfish is the DMTF standard REST API that Dell iDRAC (7/8/9) exposes for out-of-band server management. Everything hangs off /redfish/v1/. The examples below assume the TLS/cert prep from §2 has already run in the session.

5.1
Run the TLS 1.2 + certificate callback block from §2 first, or every call here fails with a trust error. Default iDRAC credentials are historically root / calvin — change them.

Setup & session authentication

Redfish supports Basic auth on every call, but the cleaner pattern is a session: POST credentials once, receive an X-Auth-Token, reuse it, then DELETE the session to log out.

idrac-01-session.ps1powershell
# ---- Prep: TLS 1.2 + trust self-signed cert (from Section 2) ----
[Net.ServicePointManager]::SecurityProtocol = [Net.SecurityProtocolType]::Tls12
[Net.ServicePointManager]::ServerCertificateValidationCallback = { $true }

$idrac = "https://192.168.10.120"
$cred  = Get-Credential   # root / calvin by default

# ---- Open a Redfish session ----
$sessionBody = @{
    UserName = $cred.UserName
    Password = $cred.GetNetworkCredential().Password
} | ConvertTo-Json

# Use Invoke-WebRequest so we can read response HEADERS (the token)
$resp = Invoke-WebRequest -Uri "$idrac/redfish/v1/SessionService/Sessions" `
    -Method Post -Body $sessionBody -ContentType "application/json" `
    -UseBasicParsing

$token       = $resp.Headers["X-Auth-Token"]      # reuse on every call
$sessionUri  = $resp.Headers["Location"]          # DELETE this to log out

$authHeader  = @{ "X-Auth-Token" = $token }
Write-Host "Session opened." -ForegroundColor Green

Read the system power state & health

idrac-02-power-state.ps1powershell
$sysUri = "$idrac/redfish/v1/Systems/System.Embedded.1"
$sys    = Invoke-RestMethod -Uri $sysUri -Headers $authHeader

[pscustomobject]@{
    Model       = $sys.Model
    ServiceTag   = $sys.SKU
    PowerState   = $sys.PowerState        # On / Off
    HealthState  = $sys.Status.Health      # OK / Warning / Critical
    BiosVersion  = $sys.BiosVersion
} | Format-List
Expected outputModel : PowerEdge R750 ServiceTag : 7XY8Z93 PowerState : On HealthState : OK BiosVersion : 1.9.2

Hardware inventory & health roll-up

idrac-03-inventory.ps1powershell
# CPU + memory summary come straight off the System object
Write-Host "CPUs : $($sys.ProcessorSummary.Count) x $($sys.ProcessorSummary.Model)"
Write-Host "RAM  : $($sys.MemorySummary.TotalSystemMemoryGiB) GiB"

# Drill into subsystems — e.g. every physical disk's health
$storeUri = "$idrac/redfish/v1/Systems/System.Embedded.1/Storage"
$ctrls    = Invoke-RestMethod -Uri $storeUri -Headers $authHeader

foreach ($c in $ctrls.Members) {
    $ctrl = Invoke-RestMethod -Uri "$idrac$($c.'@odata.id')" -Headers $authHeader
    foreach ($d in $ctrl.Drives) {
        $drive = Invoke-RestMethod -Uri "$idrac$($d.'@odata.id')" -Headers $authHeader
        [pscustomobject]@{
            Name   = $drive.Name
            SizeGB = [math]::Round($drive.CapacityBytes / 1GB, 0)
            Health = $drive.Status.Health
        }
    }
} | Format-Table -AutoSize
Expected outputCPUs : 2 x Intel(R) Xeon(R) Gold 6338 RAM : 256 GiB Name SizeGB Health ---- ------ ------ Solid State Disk 960 OK Solid State Disk 960 OK Disk.Bay.2 1863 Warning

Read then set a power action

Power actions are a POST to the system's ComputerSystem.Reset action with a ResetType. Read the allowed values first, then issue one.

idrac-04-power-action.ps1powershell
# Discover which reset types this system supports
$allowed = $sys.Actions.'#ComputerSystem.Reset'.'ResetType@Redfish.AllowableValues'
Write-Host "Allowed: $($allowed -join ', ')"
# e.g. On, ForceOff, GracefulShutdown, GracefulRestart, ForceRestart

# Issue a graceful restart
$resetUri = "$idrac/redfish/v1/Systems/System.Embedded.1/Actions/ComputerSystem.Reset"
$body     = @{ ResetType = "GracefulRestart" } | ConvertTo-Json

try {
    Invoke-RestMethod -Uri $resetUri -Method Post `
        -Headers $authHeader -Body $body -ContentType "application/json"
    Write-Host "Graceful restart issued." -ForegroundColor Green
}
catch {
    $code = $_.Exception.Response.StatusCode.value__
    Write-Warning "Reset failed (HTTP $code)"
}
Expected outputAllowed: On, ForceOff, GracefulShutdown, GracefulRestart, ForceRestart, Nmi Graceful restart issued.

Always log out

idrac-05-logout.ps1powershell
# Free the session slot — iDRAC has a small session limit
Invoke-RestMethod -Uri "$idrac$sessionUri" -Method Delete -Headers $authHeader
Write-Host "Session closed."
→
iDRAC allows only a handful of concurrent sessions. Leaked sessions eventually block all logins until they expire. Wrap the whole flow in try/finally and put the DELETE in the finally so it runs even on error.

Example — VMware ESXi (vSphere REST API)

◆ VMware vSphere · REST API

The vSphere REST API exposes VM and host management over HTTP. It's fullest against vCenter; standalone ESXi hosts expose a subset. Authentication is session-based: POST Basic credentials to the session endpoint, receive a session ID, send it as a header, and delete it when done.

5.1
Same prerequisites as iDRAC: set TLS 1.2 and the cert callback first. The endpoint path differs by version — modern vCenter (7.0u2+) uses /api/; older versions use /rest/. Examples below show the modern /api/ paths with the older path noted.

Authenticate & get a session token

esxi-01-session.ps1powershell
[Net.ServicePointManager]::SecurityProtocol = [Net.SecurityProtocolType]::Tls12
[Net.ServicePointManager]::ServerCertificateValidationCallback = { $true }

$vc   = "https://vcenter.lab.local"
$cred = Get-Credential   # e.g. administrator@vsphere.local

# Build a Basic auth header for the login call only
$pair = "$($cred.UserName):$($cred.GetNetworkCredential().Password)"
$b64  = [Convert]::ToBase64String([Text.Encoding]::ASCII.GetBytes($pair))

# POST to the session endpoint — returns a session ID string
# Modern:  /api/session      Older: /rest/com/vmware/cis/session
$sessionId = Invoke-RestMethod -Uri "$vc/api/session" -Method Post `
    -Headers @{ Authorization = "Basic $b64" }

# Reuse the session ID as a header on every later call
$sess = @{ "vmware-api-session-id" = $sessionId }
Write-Host "Authenticated to vCenter." -ForegroundColor Green
5.1
On the older /rest/ API the session ID comes back wrapped as $response.value rather than as a bare string. If $sessionId looks like an object, use $sessionId.value.

List all VMs

esxi-02-list-vms.ps1powershell
# Modern: /api/vcenter/vm    Older: /rest/vcenter/vm (data under .value)
$vms = Invoke-RestMethod -Uri "$vc/api/vcenter/vm" -Headers $sess

$vms | Select-Object vm, name, power_state, cpu_count,
    @{ N="MemoryMB"; E={ $_.memory_size_MiB } } |
    Sort-Object name | Format-Table -AutoSize
Expected outputvm name power_state cpu_count MemoryMB -- ---- ----------- --------- -------- vm-1021 dc01 POWERED_ON 2 4096 vm-1044 web-prod-01 POWERED_ON 4 8192 vm-1108 test-runner POWERED_OFF 2 4096

Filter with query parameters

The API accepts filters as query params so you don't pull everything and filter client-side.

esxi-03-filter.ps1powershell
# Only powered-on VMs, server-side filter
$uri = "$vc/api/vcenter/vm?power_states=POWERED_ON"
$on  = Invoke-RestMethod -Uri $uri -Headers $sess
Write-Host "$($on.Count) VMs are powered on."

Get detail for one VM

esxi-04-vm-detail.ps1powershell
$vmId   = "vm-1044"

    Name       = $detail.name
    Power      = $detail.power_state
    CPUs       = $detail.cpu.count
    MemoryMB   = $detail.memory.size_MiB
    GuestOS    = $detail.guest_OS

Host details

Power action on a VM & log out

esxi-06-power-and-logout.ps1powershell
# Power actions are POSTs with no body: start / stop / suspend / reset
try {
    Invoke-RestMethod -Uri "$vc/api/vcenter/vm/$vmId/power?action=start" `
        -Method Post -Headers $sess
    Write-Host "Start requested for $vmId." -ForegroundColor Green
}
catch {
    $code = $_.Exception.Response.StatusCode.value__
    # 400 often means "already in that state" — not fatal
    Write-Warning "Power action returned HTTP $code"
}
finally {
    # Always delete the session (DELETE /api/session)
    Invoke-RestMethod -Uri "$vc/api/session" -Method Delete -Headers $sess
    Write-Host "Session closed."
}
→
For heavy VMware automation, VMware's own PowerCLI module wraps all of this in friendly cmdlets (Get-VM, Start-VM). Use the raw REST approach shown here when you can't install PowerCLI, need a lightweight footprint, or are automating endpoints PowerCLI doesn't cover.
