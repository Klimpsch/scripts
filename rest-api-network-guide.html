01 · Addressing the datastore

1.1 URI structure

Every RESTCONF request is a single URL that names an exact location inside the device's configuration or operational datastore. If you can read the URI, you can read the request. A RESTCONF URL decomposes into a fixed set of segments, and each one answers a specific question.

https://scheme
R1:443host:port
/restconf/dataapi root + datastore
/ietf-interfaces:interfaces/interfaceyang module : container / list

?content=configquery
SegmentExampleWhat it selects
API root/restconfThe RESTCONF entry point. Discover it dynamically from /.well-known/host-meta rather than hardcoding.
Resource type/data · /operationsdata is the config+state datastore tree; operations invokes YANG RPCs/actions.
Module-qualified nodeietf-interfaces:interfacesThe first node after the root is prefixed by its YANG module name to disambiguate namespaces.
Path descent/interfaceEach / walks one level down the YANG tree — container into list, list into leaf.
List key=GigabitEthernet2An = after a list node selects one entry by its key leaf. Composite keys are comma-separated.
Query params?content=configModifiers: content (config/nonconfig/all), depth, fields, with-defaults.
Gotcha · key encoding

The list key sits after =, not after another /. And any reserved character in a key — a slash inside an interface name, a space, a colon — must be percent-encoded. GigabitEthernet0/0/1 becomes GigabitEthernet0%2F0%2F1. Forgetting this returns a 400 that looks like a bad path.

Note · module prefix only at the boundary

You prefix a node with its module name whenever the namespace changes — almost always the first node, and again if you cross into an augmenting module. Nodes within the same module don't repeat the prefix, which is why you see ietf-interfaces:interfaces/interface, not ietf-interfaces:interfaces/ietf-interfaces:interface.

1.2 Mapping HTTP verbs → CRUD by hand

REST's whole trick is that four CRUD operations collapse onto HTTP methods you already know. The subtlety for the exam — and for not corrupting a running config — is the difference between PUT and PATCH, and knowing which verb is idempotent.

CRUDVerbRESTCONF semanticsIdempotent?Success code
ReadGETRetrieve the resource at the target URI. Safe — never mutates state.Yes200
CreatePOSTCreate a child resource under the target. Fails if the resource already exists.No201
Create / ReplacePUTCreate or completely replace the target resource. The body is the entire new state.Yes201 / 204
UpdatePATCHMerge — modify only the leaves present in the body, leave the rest untouched.Yes*204
DeleteDELETERemove the target resource from the datastore.Yes204
Gotcha · PUT is a replace, not an edit

The single most expensive mistake here: sending a PUT to .../interface=GigabitEthernet2 with only the description in the body wipes every other leaf on that interface — IP address, shutdown state, everything — because PUT declares "this is now the complete state of the resource." To change one field on a live interface, use PATCH. Reach for PUT only when you intend to define the resource wholesale.

The same create/read, three ways

Below is one operation — read the config of GigabitEthernet2 — expressed in the three tools the exam expects you to move between fluently. They send byte-for-byte the same HTTP request; only the wrapper differs.

# curl — the raw wire

bash
# READ — GET one interface's config
curl -sk -X GET "https://R1/restconf/data/ietf-interfaces:interfaces/interface=GigabitEthernet2" \
     -H "Accept: application/yang-data+json" \
     -u "admin:cisco123"

# CREATE — POST a new interface entry under the interfaces container
curl -sk -X POST "https://R1/restconf/data/ietf-interfaces:interfaces" \
     -H "Content-Type: application/yang-data+json" \
     -H "Accept: application/yang-data+json" \
     -u "admin:cisco123" \
     -d '{ "ietf-interfaces:interface": { "name":"Loopback99", "type":"iana-if-type:softwareLoopback", "enabled":true } }'

-s silences the progress meter, -k skips cert validation on a lab device with a self-signed cert, -u does HTTP Basic. The two headers are the crux of RESTCONF content negotiation: Accept asks for JSON back, Content-Type declares the body is YANG-modeled JSON.

# Postman — the request, described

  • Method + URL: set the verb dropdown to GET; paste the full https://R1/restconf/data/... URL into the address bar.
  • Authorization tab: type Basic Auth, username admin, password cisco123 — Postman generates the Authorization: Basic <base64> header for you.
  • Headers tab: add Accept: application/yang-data+json; for writes also add Content-Type: application/yang-data+json.
  • Body tab (writes only): choose raw → JSON and paste the payload.
  • Settings: disable SSL certificate verification for lab devices (mirrors curl's -k).
Tip · Postman → code

Once a request works in Postman, use the </> Code panel to export it as a requests snippet. It's the fastest bridge from "clicked it and it worked" to "scripted it," and it keeps your headers and auth identical across the transition.

# Python requests — the scriptable equivalent

python
import requests, urllib3
urllib3.disable_warnings()  # silence self-signed cert warnings (lab only)

BASE = "https://R1/restconf/data"
HDRS = {
    "Accept": "application/yang-data+json",
    "Content-Type": "application/yang-data+json",
}
AUTH = ("admin", "cisco123")

# READ
r = requests.get(
    f"{BASE}/ietf-interfaces:interfaces/interface=GigabitEthernet2",
    headers=HDRS, auth=AUTH, verify=False,
)
print(r.status_code, r.json())

# PATCH — change ONLY the description, everything else preserved
payload = {"ietf-interfaces:interface": {"name": "GigabitEthernet2", "description": "uplink-to-core"}}
r = requests.patch(
    f"{BASE}/ietf-interfaces:interfaces/interface=GigabitEthernet2",
    headers=HDRS, auth=AUTH, json=payload, verify=False,
)
print(r.status_code)  # expect 204 No Content

Contrast: the same intent over NETCONF with ncclient

RESTCONF is the HTTP-friendly sibling of NETCONF. Both are driven by the same YANG models, but NETCONF speaks XML over SSH with an explicit <rpc> envelope and datastore locking. Knowing the parallel sharpens what RESTCONF gives you for free (statelessness, HTTP verbs) and what it gives up (transactions across multiple edits).

python
from ncclient import manager

config = """
<config>
  <interfaces xmlns="urn:ietf:params:xml:ns:yang:ietf-interfaces">
    <interface>
      <name>GigabitEthernet2</name>
      <description>uplink-to-core</description>
    </interface>
  </interfaces>
</config>"""

with manager.connect(host="R1", port=830, username="admin",
                     password="cisco123", hostkey_verify=False) as m:
    reply = m.edit_config(target="running", config=config)  # merge by default
    print(reply.ok)

02 · From model to message

2.1 YANG model → JSON payload

A JSON payload is never invented freely — it is a serialization of a YANG data model the device already publishes. Master the mapping in one direction (model → JSON) and the reverse (reading a response, or reverse-engineering a payload from show running | format) comes for free.

Model anatomy: the four node types that matter

Read enough of a YANG module and you'll see the whole language reduces, for payload purposes, to four constructs:

  • module — the namespace boundary. Its name becomes the JSON key prefix (ietf-interfaces:) at the top level.
  • container — a named grouping with no key. Serializes to a JSON object. interfaces { ... } → "interfaces": { ... }.
  • list — a keyed, repeatable node. Serializes to a JSON array of objects, each object containing its key leaf. This is the one people get wrong.
  • leaf — a single typed value. Serializes to a JSON key/value pair. enabled (boolean), name (string), mtu (number).
yang
module ietf-interfaces {                 // → namespace / key prefix
  container interfaces {                  // → JSON object
    list interface {                       // → JSON ARRAY of objects
      key "name";                         // → each object must carry "name"
      leaf name    { type string; }       // → "name":    <string>
      leaf enabled { type boolean; }      // → "enabled": <true|false>
      leaf type    { type identityref; }   // → "type": "module:identity"
    }
  }
}

The serialization rules (RFC 7951)

YANG conceptJSON encodingWatch for
Top-level node"module-name:node"Prefix required only where the namespace changes.
container{ } object—
list[ { }, { } ] arrayAlways an array, even for one entry.
leaf (int)JSON number64-bit ints (int64) are encoded as strings to survive JS precision loss.
leaf (boolean)true / falseNot the strings "true"/"false".
identityref"module:identity"e.g. "iana-if-type:ethernetCsmacd" — the module prefix is mandatory.
empty leaf[null]The quirky one. A YANG empty type serializes as an array containing null.
Gotcha · a list is always an array

When you target one list entry via the URI (...interface=GigabitEthernet2), it's tempting to send "interface": { ... } as an object. RESTCONF accepts it there because the URI already selected the entry — but the moment you POST to the parent container, the body must wrap the entry as "interface": [ { ... } ]. Mixing these up is the most common 400 in RESTCONF scripting.

Worked example: configure a subinterface with an IP

Goal: give GigabitEthernet2 a description, enable it, and assign 10.0.12.1/24. The IP address leaves live in the ietf-ip module, which augments ietf-interfaces — so we cross a namespace boundary mid-tree and must re-prefix.

http · PUT body
// PUT https://R1/restconf/data/ietf-interfaces:interfaces/interface=GigabitEthernet2
{
  "ietf-interfaces:interface": {
    "name": "GigabitEthernet2",
    "description": "link-to-R2",
    "type": "iana-if-type:ethernetCsmacd",   // identityref: module:identity
    "enabled": true,                          // boolean, not "true"
    "ietf-ip:ipv4": {                          // ← namespace crossing: re-prefix
      "address": [                              // list → ARRAY even for one IP
        {
          "ip": "10.0.12.1",
          "netmask": "255.255.255.0"
        }
      ]
    }
  }
}

Trace each rule firing: top-level node carries the ietf-interfaces: prefix; enabled is a bare boolean; type is a prefixed identityref; crossing into IP config re-prefixes to ietf-ip:; and address — a YANG list — is an array even though there's exactly one address. Because we used PUT, this body is the complete definition of the interface; any leaf omitted here is reset to its default.

Note · how to never guess a payload

Don't hand-write payloads from memory. GET the resource first, copy the exact JSON the device returns, edit the leaves you care about, and send it back with PATCH (merge) or PUT (replace). The device's own response is the authoritative template for its models and versions.

03 · Surviving real networks

3.1 Pagination

Controller APIs (DNA Center, Meraki, ISE) cap how much they'll return per call. A client that reads only the first page silently drops data — the worst kind of bug because it looks like it worked. Two dominant styles:

StyleMechanismStop condition
Offset / limitRequest ?limit=500&offset=0, then offset=500, 1000…A page returns fewer than limit items.
Cursor / linkServer returns a next token or a Link: <url>; rel="next" header.No next link is present.
python
def get_all(session, url, page_size=500):
    """Offset pagination — accumulate every page into one list."""
    items, offset = [], 0
    while True:
        r = session.get(url, params={"limit": page_size, "offset": offset})
        r.raise_for_status()
        batch = r.json().get("response", [])
        items.extend(batch)
        if len(batch) < page_size:      # short page ⇒ last page
            return items
        offset += page_size

3.2 OAuth2 authorization + refresh

Basic Auth is fine for a lab router; controllers use OAuth2 bearer tokens with short lifetimes. The pattern that matters operationally is token refresh: an access token expires in minutes, and rather than re-running the full login you exchange a longer-lived refresh token for a new access token.

python
import time, requests

class OAuth2Token:
    def __init__(self, token_url, client_id, client_secret):
        self.token_url, self.cid, self.secret = token_url, client_id, client_secret
        self.access = self.refresh = None
        self.expires_at = 0

    def _post(self, data):
        r = requests.post(self.token_url, data=data,
                          auth=(self.cid, self.secret), timeout=10)
        r.raise_for_status()
        t = r.json()
        self.access = t["access_token"]
        self.refresh = t.get("refresh_token", self.refresh)
        # refresh 30s early to dodge clock skew & in-flight expiry
        self.expires_at = time.time() + t["expires_in"] - 30

    def bearer(self):
        if self.access is None:
            self._post({"grant_type": "client_credentials"})
        elif time.time() >= self.expires_at:
            self._post({"grant_type": "refresh_token",
                        "refresh_token": self.refresh})
        return {"Authorization": f"Bearer {self.access}"}
Tip · refresh early, not on failure

Refreshing reactively (wait for a 401, then refresh, then retry) works but doubles latency on every expiry boundary and races under concurrency. Refreshing proactively a few seconds before expires_in — as above — keeps the hot path clean. Keep the 401-retry as a backstop, not the primary mechanism.

3.3 HTTP session reuse

A fresh requests.get() opens a new TCP + TLS connection every call. Against a device you're hitting dozens of times, that handshake cost dominates. A Session pools connections (HTTP keep-alive) and persists headers, auth, and cookies across requests.

python
import requests
from requests.adapters import HTTPAdapter

s = requests.Session()
s.headers.update({"Accept": "application/yang-data+json"})
s.verify = False

# widen the connection pool so bursts don't serialize on one socket
adapter = HTTPAdapter(pool_connections=10, pool_maxsize=50)
s.mount("https://", adapter)

# every call now reuses a warm TLS connection
r1 = s.get("https://R1/restconf/data/...")
r2 = s.get("https://R1/restconf/data/...")  # no new handshake

3.4 Retry-After & exponential backoff

A 429 Too Many Requests or 503 is not a failure to abort on — it's the server asking you to slow down. If it sends a Retry-After header, honor it exactly. Otherwise back off exponentially with jitter so a fleet of clients doesn't retry in lockstep and re-create the stampede.

python
import time, random

def request_with_backoff(session, method, url, max_tries=5, **kw):
    for attempt in range(max_tries):
        r = session.request(method, url, **kw)
        if r.status_code not in (429, 503):
            return r                                # success or a non-retryable code
        # server told us how long? obey it. otherwise 2^n with jitter
        wait = r.headers.get("Retry-After")
        wait = float(wait) if wait else (2 ** attempt) + random.random()
        time.sleep(wait)
    r.raise_for_status()                          # exhausted retries → surface it
    return r
Gotcha · never retry blindly

Only retry on 429, 503, and transient network errors. Retrying a 400 or 404 just hammers a request that will never succeed. And never retry a non-idempotent POST without a mechanism to detect partial success — you can create duplicate resources.

3.5 Status-code branching

The whole point of HTTP status codes is that the class (first digit) tells you the handling strategy before you ever parse the body.

ClassMeaningRepresentative codesClient action
2xxSuccess200 OK · 201 Created · 204 No ContentParse body (or trust the empty 204). Done.
3xxRedirection301 · 307Follow (requests does this by default) — but re-check auth on cross-host redirects.
4xxClient error — you are wrong400 bad body · 401 auth · 403 perms · 404 path · 409 conflictDo not retry unchanged. Fix the request. 401 ⇒ refresh token once, then retry.
5xxServer error — they are wrong500 · 502 · 503 · 504Retry with backoff. If it persists, it's an outage, not your bug.
04 · Capstone

4.0 Build one robust API client

Everything above converges here. This single class composes token refresh, session reuse, retry/backoff, pagination, and status branching behind clean CRUD methods. It's the shape you'd actually ship — read it as the summary of the whole guide.

python · net_client.py
import time, random, requests, urllib3
from requests.adapters import HTTPAdapter
urllib3.disable_warnings()

class NetworkAPIError(Exception): pass

class RestconfClient:
    """A production-shaped RESTCONF/REST client:
       OAuth2 refresh · pooled session · retry/backoff · pagination · status branching."""

    RETRYABLE = {429, 500, 502, 503, 504}

    def __init__(self, base_url, token_url, client_id, client_secret,
                 verify=False, max_tries=5):
        self.base = base_url.rstrip("/")
        self.token_url, self.cid, self.secret = token_url, client_id, client_secret
        self.max_tries = max_tries
        self._access = self._refresh = None
        self._expires_at = 0.0

        # --- pooled, keep-alive session (§3.3) ---
        self.s = requests.Session()
        self.s.verify = verify
        self.s.headers.update({
            "Accept": "application/yang-data+json",
            "Content-Type": "application/yang-data+json",
        })
        self.s.mount("https://", HTTPAdapter(pool_connections=10, pool_maxsize=50))

    # ---------- auth (§3.2) ----------
    def _fetch_token(self, data):
        r = requests.post(self.token_url, data=data,
                          auth=(self.cid, self.secret), verify=self.s.verify, timeout=10)
        if not r.ok:
            raise NetworkAPIError(f"token request failed: {r.status_code}")
        t = r.json()
        self._access = t["access_token"]
        self._refresh = t.get("refresh_token", self._refresh)
        self._expires_at = time.time() + t.get("expires_in", 3600) - 30

    def _auth_header(self):
        if self._access is None:
            self._fetch_token({"grant_type": "client_credentials"})
        elif time.time() >= self._expires_at:
            self._fetch_token({"grant_type": "refresh_token", "refresh_token": self._refresh})
        return {"Authorization": f"Bearer {self._access}"}

    # ---------- core request w/ retry + branching (§3.4, §3.5) ----------
    def _request(self, method, path, **kw):
        url = path if path.startswith("http") else f"{self.base}/{path.lstrip('/')}"
        for attempt in range(self.max_tries):
            headers = {**kw.pop("headers", {}), **self._auth_header()}
            r = self.s.request(method, url, headers=headers, timeout=30, **kw)

            if r.status_code == 401 and attempt == 0:
                self._access = None            # force one refresh, then retry
                continue
            if r.status_code in self.RETRYABLE:
                w = r.headers.get("Retry-After")
                time.sleep(float(w) if w else (2 ** attempt) + random.random())
                continue
            if 400 <= r.status_code < 500:
                raise NetworkAPIError(f"{r.status_code} client error: {r.text[:200]}")
            return r
        raise NetworkAPIError(f"exhausted {self.max_tries} retries on {method} {url}")

    # ---------- CRUD surface (§1.2) ----------
    def get(self, path):        return self._request("GET", path).json()
    def create(self, path, body): return self._request("POST", path, json=body)
    def replace(self, path, body):return self._request("PUT", path, json=body)
    def update(self, path, body): return self._request("PATCH", path, json=body)
    def delete(self, path):     return self._request("DELETE", path)

    # ---------- pagination helper (§3.1) ----------
    def get_all(self, path, key="response", page_size=500):
        items, offset = [], 0
        while True:
            r = self._request("GET", path,
                              params={"limit": page_size, "offset": offset})
            batch = r.json().get(key, [])
            items.extend(batch)
            if len(batch) < page_size:
                return items
            offset += page_size


# ---------- usage ----------
if __name__ == "__main__":
    api = RestconfClient(
        base_url="https://R1/restconf/data",
        token_url="https://R1/auth/token",
        client_id="netops", client_secret="s3cret",
    )

    # READ one interface
    gi2 = api.get("ietf-interfaces:interfaces/interface=GigabitEthernet2")

    # UPDATE just the description (merge, non-destructive)
    api.update("ietf-interfaces:interfaces/interface=GigabitEthernet2",
               {"ietf-interfaces:interface": {"name": "GigabitEthernet2",
                                            "description": "managed-by-api"}})
Tip · what makes this "robust"

Notice what the CRUD methods don't contain: no auth logic, no retry loops, no pagination. Every cross-cutting concern lives once in _request, so the surface you call stays a clean four-verb mapping. That separation — thin CRUD over a fortified transport core — is the pattern the exam is really testing you to recognize.
