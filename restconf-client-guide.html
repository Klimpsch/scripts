00

What an API — and an API client — actually are

Before a single line of the script makes sense, two words have to be nailed down, because the whole design is a response to what they mean.

The API the contract

An API — Application Programming Interface — is a published contract that lets one piece of software drive another without touching its internals. On a network device, the API is the promise the platform makes: "send me an HTTP request shaped like this, to a URL shaped like that, carrying credentials I recognise, and I will read, change, or delete a specific piece of my running configuration or state, then answer you in a structured format."

The key word is contract. You are not SSHing in and screen-scraping show output that changes format between IOS releases. You are calling a stable, versioned, machine-oriented surface. On a router that surface is typically RESTCONF (HTTP + YANG-modelled data) or NETCONF (XML over SSH). The script in front of us speaks RESTCONF.

The API client the driver

An API client is the code on your side that knows how to hold up your end of that contract correctly, every time, so the rest of your program doesn't have to. Left to itself, a raw HTTP call has to worry about a dozen cross-cutting concerns: attaching a valid token, re-using TCP connections, deciding whether a 503 is fatal or worth retrying, converting a 404 into a Python exception, walking paginated result sets, and so on.

The client's job is to absorb all of that once and expose a small, honest interface upward. When the rest of your automation calls api.get(...), it should be able to trust that authentication, retries, connection re-use, and error translation already happened. That single sentence is the design brief for the entire RestconfClient class.

Mental model

Think of the API as the device's published port and protocol, and the API client as a well-behaved peer that already speaks it fluently. The value of the client is not any one feature — it's that it makes every call downstream boring, predictable, and correct.

A good API client is measured by how little the code that uses it has to know.

01

REST, RESTCONF, and the CRUD surface

REST in one breath

REST (Representational State Transfer) is an architectural style, not a protocol. Its relevant tenets for us are few but strict: everything is a resource identified by a URL; you act on resources with a small fixed set of HTTP verbs; each request is stateless (it carries everything the server needs — including your auth — because the server remembers nothing between calls); and the server reports outcomes with HTTP status codes. Every architectural decision in this script is downstream of those four facts.

RESTCONF: REST wearing a YANG jacket

RESTCONF (RFC 8040) is the IETF's binding of REST onto network configuration. It keeps REST's verbs and status codes but pins down the specifics: resources live under a /restconf/data/ root; the resource path is a YANG data path such as ietf-interfaces:interfaces/interface=GigabitEthernet2; and bodies are YANG-modelled JSON tagged with the media type application/yang-data+json. That media type is exactly what the client sets as its default Accept and Content-Type — the device would reject or mis-handle plain application/json.

That interface=GigabitEthernet2 syntax is RESTCONF's way of selecting one entry from a YANG list by its key. It is the URL-level expression of the same list-keyed structure you'd see in a pyang tree as interface* [name].

CRUD ↔ HTTP ↔ RESTCONF the core mapping

CRUD — Create, Read, Update, Delete — is the four-verb vocabulary of persistent data everywhere in computing. REST maps CRUD onto HTTP verbs, and RESTCONF inherits that mapping almost unchanged. This table is the conceptual spine of the whole client; the CRUD methods near the bottom of the script are nothing more than one thin line per row here.

The PUT vs PATCH trap

This is the single most consequential distinction in the table for a network engineer. PUT replaces the whole resource — send an interface body without its IP block and you have just deleted that interface's addressing. PATCH merges — it changes only the leaves you name. The script deliberately exposes both as separate verbs (replace() vs update()) precisely so the choice is explicit at every call site, never accidental.

Idempotency — why it matters for retries

GET, PUT, and DELETE are idempotent: performing them once or five times leaves the server in the same state. POST is not — two POSTs may create two resources. Hold onto this fact; it is the hidden justification for how aggressively (or cautiously) the retry logic in §05 is allowed to behave.

The class at ten thousand feet

Before the line-by-line dissection, hold the whole shape in your head. The class is organised in five concentric rings, from outermost concern to innermost.

▚ Layered responsibilities, outer → inner
5
CRUD surface & pagination

The public API: get, create, replace, update, delete, get_all. This is all the outside world touches.

4
The request engine — _request()

Every verb funnels through here. Retries, back-off, status-code branching, and 401-driven re-auth all live in one place.

3
Auth layer — _auth_header() / _fetch_token()

Lazily obtains and transparently refreshes an OAuth2 bearer token, handing a ready Authorization header upward on demand.

Base URL, token endpoint, credentials, and the mutable token/expiry fields the auth layer reads and writes.

Notice the discipline: a caller at ring 5 never reaches past ring 4. They never see a token, never see a retry, never see a raw status code. Each ring trusts the ring beneath it to have already done its job. That layering is what makes the top surface so small.

Naming convention

Methods prefixed with a single underscore — _fetch_token, _auth_header, _request — are Python's soft signal for "internal, not part of the public contract." The un-prefixed methods are the supported surface. This is the code telling you, by convention, exactly which ring each piece belongs to.

03

Construction & the pooled session

__init__ & session setup
class RestconfClient:
    RETRYABLE = {429, 500, 502, 503, 504}

    def __init__(self, base_url, token_url, client_id, client_secret,
                 verify=False, max_tries=5):
        self.base = base_url.rstrip("/")
        self.token_url, self.cid, self.secret = token_url, client_id, client_secret
        self.max_tries = max_tries
        self._access = self._refresh = None
        self._expires_at = 0.0

        # --- pooled, keep-alive session (§3.3) ---
        self.s = requests.Session()
        self.s.verify = verify
        self.s.headers.update({
            "Accept": "application/yang-data+json",
            "Content-Type": "application/yang-data+json",
        })
        self.s.mount("https://", HTTPAdapter(pool_connections=10, pool_maxsize=50))

The class-level constant

RETRYABLE sits at class scope, not instance scope, on purpose: it is shared, immutable policy — the set of HTTP status codes that represent transient failures worth retrying. 429 (Too Many Requests) plus the 5xx server errors. A 4xx like 400 or 404 is your fault and won't improve on retry, so it is pointedly excluded. Defining it once at class level means every instance references the same object instead of rebuilding the set per call.

What the constructor stores, and why

base.rstrip("/")
The API root. Stripping any trailing slash now means URL assembly later can safely do f"{base}/{path}" without producing a double slash. A tiny normalisation that removes a whole class of bugs.
token_url, cid, secret
The OAuth2 credentials, kept separate from the API base because the token endpoint is frequently a different host (an identity provider) than the resource server.
_access, _refresh
Initialised to None — "no token yet." The chained assignment sets both in one line.
_expires_at = 0.0
Unix timestamp 0 = 1970. The first auth check will always see the token as long expired and fetch one. A deliberate way to force lazy first-fetch without a special "have I ever fetched?" flag.

The session — the quiet performance win §3.3

This is the part that separates a toy script from a production client. Instead of calling requests.get(...) ad hoc (which opens and tears down a fresh TCP + TLS connection every single call), the client builds one requests.Session and reuses it.

  • Keep-alive connection re-use. The session holds TCP connections open. For HTTPS, the expensive part is the TLS handshake — re-using a connection amortises that cost across many calls. In a loop pulling a thousand interfaces, this is the difference between snappy and painful.
  • Default headers set once. Accept and Content-Type are attached to the session, so every request inherits the correct RESTCONF media type without repeating it.
  • Explicit connection pool. The mounted HTTPAdapter tunes the pool: pool_connections=10 distinct host-pools, pool_maxsize=50 connections per pool. That headroom matters the moment you drive the client concurrently across many targets.
  • verify=False, deliberately. Lab and pre-prod devices ship self-signed certs; disabling verification (and silencing the urllib3 warning at the top of the file) keeps the noise down. In production you would flip this to a CA bundle path — flagged again in §10.
Why store self.s at all

Every later request goes through self.s.request(...), not requests.request(...). The stored session is the shared transport ring. Building it in the constructor means it is created exactly once per client and lives for the client's whole lifetime.

04

OAuth2 — token fetch & transparent refresh

These two methods are the auth ring. Together they guarantee that any request leaving the client carries a currently-valid bearer token, while the caller never thinks about tokens at all.

auth (§3.2)
    def _fetch_token(self, data):
        r = requests.post(self.token_url, data=data,
                          auth=(self.cid, self.secret), verify=self.s.verify, timeout=10)
        if not r.ok:
            raise NetworkAPIError(f"token request failed: {r.status_code}")
        t = r.json()
        self._access = t["access_token"]
        self._refresh = t.get("refresh_token", self._refresh)
        self._expires_at = time.time() + t.get("expires_in", 3600) - 30

    def _auth_header(self):
        if self._access is None:
            self._fetch_token({"grant_type": "client_credentials"})
        elif time.time() >= self._expires_at:
            self._fetch_token({"grant_type": "refresh_token", "refresh_token": self._refresh})
        return {"Authorization": f"Bearer {self._access}"}

OAuth2 in the client-credentials flow

OAuth2 is a token-based authorization framework. The client here uses the client-credentials grant — the machine-to-machine flow with no human user in the loop. The logic is: present your client_id / client_secret to a token endpoint, receive a short-lived access token, and thereafter prove yourself to the resource server by carrying that token in an Authorization: Bearer … header. The token, not the raw secret, rides along on every API call — so the secret is exposed to exactly one endpoint instead of every device.

_fetch_token() — the network step

  • Basic-auths the client itself. auth=(cid, secret) sends the client credentials as HTTP Basic to the token endpoint. This authenticates the application, distinct from the bearer token that later authenticates each request.
  • Uses bare requests.post, not the session. A subtle, correct choice: the token fetch must not inherit the session's default application/yang-data+json headers or its bearer state — a token request is form-encoded and needs no bearer. Keeping it off the session avoids header cross-contamination.
  • Fails loud. if not r.ok converts any non-2xx token response into a domain-specific NetworkAPIError rather than letting a broken login masquerade as a valid session downstream.
  • Preserves an existing refresh token. t.get("refresh_token", self._refresh) — if the response omits a new refresh token, keep the one already held instead of clobbering it with None.
  • The minus-30 skew guard. expires_at = now + expires_in − 30 converts the server's relative lifetime into an absolute deadline, then backdates it 30 seconds. This proactively refreshes just before true expiry, dodging the race where a token looks valid at check-time but dies mid-flight, and absorbing minor clock skew between client and server.

_auth_header() — the decision, made lazily

This is a three-branch decision tree evaluated on every request:

▚ token lifecycle decision
A
No token yet (_access is None)

First call in the client's life → fetch fresh via client_credentials.

B
Token exists but is past its (skew-adjusted) deadline

Refresh via refresh_token grant — cheaper than a full re-auth where the provider supports it.

C
Token still valid

Neither branch fires — zero network calls. Return the cached header immediately.

Branch C is the common case and the whole point: once warmed, the auth ring is nearly free. The method always ends by returning a ready-to-merge {"Authorization": "Bearer …"} dict, so the request engine can splice it into headers without knowing anything about how it was obtained.

The latent edge — pure client-credentials has no refresh token

Many providers issuing a client-credentials token return no refresh token at all. If such a token expires, branch B would send "refresh_token": None and fail. A CCIE-grade hardening is to make expiry re-run the client_credentials grant when self._refresh is None. Noted again in §10 — but see how the retry engine in §05 already provides a safety net for exactly this.

05

The request engine — retry, back-off & status branching

This single method is the beating heart of the client. Every CRUD verb, and pagination, funnels through it — which is exactly why the resilience logic can live here once and cover everything.

_request (§3.4, §3.5)
    def _request(self, method, path, **kw):
        url = path if path.startswith("http") else f"{self.base}/{path.lstrip('/')}"
        for attempt in range(self.max_tries):
            headers = {**kw.pop("headers", {}), **self._auth_header()}
            r = self.s.request(method, url, headers=headers, timeout=30, **kw)

            if r.status_code == 401 and attempt == 0:
                self._access = None            # force one refresh, then retry
                continue
            if r.status_code in self.RETRYABLE:
                w = r.headers.get("Retry-After")
                time.sleep(float(w) if w else (2 ** attempt) + random.random())
                continue
            if 400 <= r.status_code < 500:
                raise NetworkAPIError(f"{r.status_code} client error: {r.text[:200]}")
            return r
        raise NetworkAPIError(f"exhausted {self.max_tries} retries on {method} {url}")

URL assembly — accept both relative and absolute

url = path if path.startswith("http") else f"{self.base}/{path.lstrip('/')}". A caller can pass a short relative path (ietf-interfaces:interfaces) or a fully-qualified URL. The latter is essential for pagination, where the server may hand back an absolute "next page" link that should be used verbatim. The lstrip("/") pairs with the constructor's rstrip("/") to guarantee exactly one joining slash.

The retry loop — one guarded attempt per iteration

The whole body is a for attempt in range(self.max_tries) loop. Each pass either returns a good response, continues to retry, or raises. Falling off the end of the loop means every attempt was consumed — hence the final "exhausted retries" raise. Walking the branches in order:

1 · Fresh auth header, every attempt

headers = {**kw.pop("headers", {}), **self._auth_header()}. Two things happen. First, any caller-supplied headers are merged with the auth header — and because _auth_header() is spread second, the client's Authorization always wins, so a caller can't accidentally override it. Second, kw.pop("headers", …) removes headers from kw so it isn't passed twice into self.s.request(...). And crucially the auth header is rebuilt inside the loop — so if attempt 0 triggered a token refresh, attempt 1 picks up the new token automatically.

2 · The 401 self-heal § re-auth

if r.status_code == 401 and attempt == 0: → set self._access = None and continue. A 401 Unauthorized means the token was rejected — perhaps it expired a hair earlier than predicted, or was revoked. Nulling _access forces branch A of _auth_header() on the retry, minting a brand-new token. The and attempt == 0 guard is important: it permits exactly one re-auth attempt, so a genuinely bad credential can't spin the loop forever swapping tokens. This is also the safety net for the missing-refresh-token edge from §04 — an expiry that slips through gets caught here as a 401 and healed with a full re-auth.

3 · Transient failures & exponential back-off § back-off

if r.status_code in self.RETRYABLE: handles 429/5xx. The wait is chosen with care:

  • Honour Retry-After if present. When the server explicitly tells you how long to wait (common with 429), obey it: float(w).
  • Otherwise exponential back-off with jitter. (2 ** attempt) + random.random() yields ≈1s, 2s, 4s, 8s… growing delays that ease pressure on a struggling server. The added random() is jitter — it de-synchronises many clients retrying at once, preventing a thundering-herd stampede where everyone retries on the same beat.

4 · Client errors fail fast

if 400 <= r.status_code < 500: → raise immediately. A 4xx that isn't the special-cased 401 (or the 429 already handled above) is a your-request-is-wrong error: a malformed body, a bad YANG path, a 404. Retrying is pointless and wasteful, so the client converts it straight into a NetworkAPIError carrying the code and a [:200] slice of the body — enough context to debug without dumping a giant payload into the exception.

5 · Success

Anything that survives all four branches is a 2xx/3xx and gets returned as the raw Response. The ordering of these branches is itself the logic: 401 before generic-4xx (so 401 self-heals instead of raising), retryable before 4xx (so 429 waits instead of raising), and the plain return last.

Idempotency & the honest caveat

Recall §01: POST is not idempotent. This engine retries all verbs uniformly. For GET/PUT/DELETE that's perfectly safe. For a retried POST (a create) that actually succeeded server-side but whose response was lost, a retry could create a duplicate. In practice RESTCONF create is often naturally idempotent (a second create of an existing key returns 409, which falls into fail-fast) — but a rigorous client would gate POST retries or require an idempotency key. Worth knowing exactly where the sharp edge is.

06

The CRUD surface — five honest one-liners

Here is the payoff for all that machinery. Because _request() already carries auth, retries, and error handling, each public verb is a single trivial line. This is what "absorb complexity once, expose it simply" looks like in the flesh.

CRUD surface (§1.2)
    def get(self, path):         return self._request("GET", path).json()
    def create(self, path, body): return self._request("POST", path, json=body)
    def replace(self, path, body):return self._request("PUT", path, json=body)
    def update(self, path, body): return self._request("PATCH", path, json=body)
    def delete(self, path):      return self._request("DELETE", path)
  • get() returns parsed JSON, not a Response. Reads are the one verb whose body is almost always what you want, so it calls .json() for you. The write verbs return the raw Response instead, because callers often care about the status code (a 201 Created vs a 204 No Content) more than a body that is frequently empty.
  • json=body does two jobs. The requests library serialises the dict to a JSON string and would set a JSON content-type — but here the session already pins application/yang-data+json, which correctly survives, giving RESTCONF exactly the media type it expects.
  • The naming encodes semantics. replace (PUT) vs update (PATCH) is not cosmetic — it forces the destructive-vs-merge decision from §01 into the method name, so a code reviewer sees the intent at the call site.

The measure of the design: five verbs, five lines, zero repetition of auth, retry, or error logic.

07

Pagination — walking large result sets

pagination helper (§3.1)
    def get_all(self, path, key="response", page_size=500):
        items, offset = [], 0
        while True:
            r = self._request("GET", path,
                              params={"limit": page_size, "offset": offset})
            batch = r.json().get(key, [])
            items.extend(batch)
            if len(batch) < page_size:
                return items
            offset += page_size

APIs cap how much they'll return per call to protect themselves. Asking for "all interfaces" on a large controller could mean tens of thousands of rows; the server hands them back in pages. get_all hides that mechanics behind one call that returns the complete list.

  • Offset/limit windowing. Each iteration requests page_size rows starting at offset, then advances the offset by a page. Classic offset pagination.
  • The termination signal is a short page. if len(batch) < page_size — when the server returns fewer rows than requested, that page is the last one. Return everything accumulated so far. A full page implies "there may be more," so loop again.
  • Configurable envelope key. Real APIs wrap the list under different top-level keys — response, data, collection. The key parameter lets one helper serve many APIs, and .get(key, []) degrades to an empty list rather than a KeyError if the envelope is unexpectedly shaped.
  • It reuses _request. So every page inherits auth, retry, and back-off for free. Pagination didn't have to re-solve any of those.
A subtlety worth naming

Offset pagination has a known weakness: if rows are inserted or deleted while you page, the window can skip or double-count. Cursor/link-based pagination (following a server-supplied "next" URL — which the absolute-URL handling in §05 already supports) is more robust for volatile data. For device inventories that change slowly, offset is perfectly fine.

08

Putting it to work

usage
if __name__ == "__main__":
    api = RestconfClient(
        base_url="https://R1/restconf/data",
        token_url="https://R1/auth/token",
        client_id="netops", client_secret="s3cret",
    )

    # READ one interface
    gi2 = api.get("ietf-interfaces:interfaces/interface=GigabitEthernet2")

    # UPDATE just the description (merge, non-destructive)
    api.update("ietf-interfaces:interfaces/interface=GigabitEthernet2",
               {"ietf-interfaces:interface": {"name": "GigabitEthernet2",
                                            "description": "managed-by-api"}})

Read the two operations against everything above. The get call triggers the entire machine on its first invocation: _request → _auth_header sees _access is None → _fetch_token does the client-credentials handshake → the GET goes out over the pooled session with a bearer token → any transient 5xx would back off and retry → the JSON body is parsed and handed back. The caller wrote one line and got all of it.

The update call is the §01 PATCH-merge lesson in practice. The body names only name (the list key, always required to identify the row) and description. Because it's a PATCH, the interface's IP addressing, type, and enabled state are all untouched. The same payload sent through replace() (PUT) would have wiped every unmentioned leaf — which is precisely why the client made you choose the verb by name.

The whole thesis, in two calls

Nothing at this call site mentions tokens, sessions, retries, back-off, or status codes. That absence is the entire value proposition of an API client. The complexity didn't vanish — it was paid for once, in the rings below, so it never has to be paid again here.

09

Why this shape wins — benefits & use cases

Benefits

PropertyHow the design delivers it
CorrectnessAuth, media types, and error translation happen in exactly one place, so they can't be forgotten or done inconsistently at a call site.
ResilienceRetry + exponential back-off + jitter + 401 self-heal turn transient network and server hiccups into invisible non-events.
PerformanceThe pooled keep-alive session amortises TLS handshakes across thousands of calls — decisive at fleet scale.
ReadabilityCall sites read as intent (api.update(path, body)), not plumbing. Reviews focus on what changed, not how it was sent.
SafetySeparate replace/update verbs make the destructive-vs-merge choice explicit and auditable.
TestabilityOne choke-point (_request) is trivial to mock; the CRUD verbs need almost no tests of their own.

Use cases

  • Config compliance & drift remediation. Sweep a fleet, GET each device's config, diff against intent, PATCH the deltas — all with automatic retry across flaky WAN links.
  • Bulk provisioning. Push interface, routing, or ACL config to hundreds of devices in a loop, the connection pool keeping it fast and the back-off keeping it polite.
  • Inventory & telemetry collection. get_all across large controllers (DNA/Catalyst Center, SD-WAN vManage) to build a source-of-truth database.
  • CI/CD network pipelines. A test stage that applies candidate config to a CML lab, validates, then rolls back — the client's fail-fast 4xx handling surfaces bad YANG immediately.
  • Event-driven automation. A webhook handler that reacts to an alarm by reading and adjusting device state, trusting the client to handle token lifecycle unattended for weeks.
10

Where a CCIE would sharpen it

The script is genuinely production-shaped, but a senior reviewer would flag a handful of edges. None are bugs in the common path; all are the difference between "works" and "trusted in the core."

  • Client-credentials with no refresh token. As noted in §04, branch B can send refresh_token: None. Make expiry fall back to a full client_credentials grant when self._refresh is None. (Today the §05 401-heal masks this, but relying on a round-trip failure to trigger re-auth is wasteful.)
  • POST retries aren't idempotency-guarded. Per §05, uniformly retrying POST risks duplicate creates on a lost success response. Gate POST out of the retry set, or thread an idempotency key.
  • verify=False by default. Fine for lab; dangerous in production, where it silently disables TLS trust. Default to a CA bundle and make disabling it a conscious act.
  • Token fetch isn't retried. _fetch_token uses bare requests.post with no back-off. If the identity provider blips, the whole client fails on first auth. The same retryable-status logic deserves to wrap the token call.
  • No concurrency guard on the token. Under threads, several callers can enter _fetch_token at once and stampede the token endpoint. A lock around the refresh makes it thread-safe — worth it given the pool is sized for parallelism.
  • Retry-After header assumed numeric. RFC 7231 permits an HTTP-date form too; float(w) would raise on that. A robust parse handles both shapes.
  • A total time budget. Five retries with exponential back-off can stall a call for ~30s+. A wall-clock deadline across attempts gives callers a predictable worst case.
The takeaway

Every item above is an edge, not a flaw in the spine. The architecture — layered rings, one choke-point, explicit verbs, resilient transport — is exactly right. That's the real lesson: get the shape correct first, and the hardening becomes a checklist rather than a rewrite.
